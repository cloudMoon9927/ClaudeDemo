## 🚨 关键问题1：监管合规风险（致命问题）

### 问题描述
根据2024年监管政策，**监管部门已要求基金公司下线基金实时净值估算功能**。原因包括：
- 估值与真实净值存在差异，容易误导投资者
- 不同平台估值标准不一，产生争议
- 鼓励投资者频繁交易，与长期持有理念相悖

文档中完全没有提到这个监管风险，这是一个致命遗漏。

### 优化建议

**方案A：调整产品定位（推荐）**
1. 从"实时估值工具"转向"投资决策辅助工具"
2. 弱化"实时估值"宣传，强调"投资分析"和"持仓管理"
3. 核心功能调整为：
   - 持仓管理与分析
   - 市场信息聚合
   - 估值回溯与统计
   - 投资决策辅助（基于历史数据）

**方案B：差异化竞争**
1. 不做盘中实时估值，做"收盘后净值预测"
2. 强调"估值准确率统计"，让用户看到估值的可靠性
3. 提供"估值偏差分析"，帮助用户理解估值的不确定性

**方案C：合规先行**
1. 在产品中显著位置添加免责声明
2. 明确标注"估值仅供参考，不构成投资建议"
3. 提供"估值准确率"展示，让用户自行判断

### 具体修改建议
1. 产品需求文档中增加"监管合规风险与应对"章节
2. 在免责声明部分增加监管要求的说明
3. 调整功能优先级，将"持仓管理"和"投资分析"提升为核心功能
4. 估值功能增加显著的置信度展示和风险提示

## ⚠️ 关键问题2：架构过重与定位矛盾

### 问题描述
产品定位："轻量化、高精准、实时更新"  
实际架构：6个微服务 + Kafka + K8s集群 + 3种数据库 + Redis集群

这个架构的运维成本和复杂度远高于"轻量化"定位。

### 优化建议

**用户确认的简化方案：**
- 前后端分离
- 数据库：MySQL + Redis
- 消息队列：RabbitMQ（按需使用）

### 具体修改建议
1. 架构设计文档增加"架构演进路线"章节
2. 简化MVP阶段架构为3个核心服务：
   - **core-service**：基金信息、用户管理、持仓管理
   - **valuation-service**：估值计算、估值推送
   - **market-service**：行情聚合、市场数据
3. 部署简化为Docker Compose编排（3个服务容器 + MySQL + Redis）

## ⚠️ 关键问题3：估值算法不透明

### 问题描述
文档强调"逻辑透明"，但没有详细说明估值算法。

### 需要补充的内容

**1. 股票型基金估值算法**
```
估值涨跌幅 = Σ(重仓股权重 × 重仓股涨跌幅) / Σ重仓股权重
```
- 需要说明权重计算方法
- 需要说明如何处理非前十大重仓股的仓位（假设与重仓股一致？）
- 需要说明估值误差的来源

**2. 债券型基金估值算法**
- 需要单独说明
- 久期、信用利差等因素如何考虑

**3. QDII基金估值算法**
- 时差问题如何处理
- 汇率如何换算

**4. 置信度计算模型**
```
置信度 = f(持仓透明度, 数据新鲜度, 市场波动率, 历史估值准确率)
```

**5. 估值校准策略**
- 每日收盘后对比估值与实际净值
- 统计偏差分布
- 动态调整模型参数

### 优化建议
1. 补充"估值算法设计"章节
2. 详细说明每种基金类型的估值方法
3. 提供置信度计算模型
4. 说明估值误差的范围和来源

## ⚠️ 关键问题4：OCR技术风险

### 问题描述
OCR截图导入是亮点功能，但存在以下风险：
1. PaddleOCR.js WASM包体积大（~10MB），首次加载慢
2. 支付宝截图版式经常变化，模板匹配需要持续维护
3. 识别准确率受截图质量影响大
4. 解析逻辑复杂（需要识别基金名称、代码、份额、市值等）

### 优化建议
1. **优先级调整**：OCR作为v2.0功能，v1.0先做手动录入和Excel导入
2. **MVP策略**：先支持1-2种最典型的截图版式
3. **用户体验**：设计"识别结果确认"流程，让用户校对
4. **降级方案**：OCR失败时提供手动输入界面
